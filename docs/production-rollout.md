# 本番反映手順書

対象は金型ショット数管理アプリです。本書は実行順序と確認項目を定義するものであり、記載時点では本番DB・Render本番設定・本番サービスを変更しません。

## 0. 実行開始条件

- PR #1のDraft解除と`main`へのマージが別途承認されている
- GitHub Actionsが成功している
- RenderのLinux環境で`npm ci`が成功するよう、Windows専用テスト依存を本番インストールから分離している
- 旧メンテナンスアプリの担当者、作業時間帯、切り戻し判断者が決まっている
- ショット数管理専用の本番DBを使用し、旧アプリのDBを流用しない方針が承認されている

## 1. 本番データのバックアップ

1. 旧メンテナンスアプリのNeonプロジェクトで、バックアップ／復元機能または`pg_dump`を使える状態にする。
2. `molds`と`maintenance_logs`を含む旧DB全体をバックアップする。
3. バックアップ先、取得時刻、対象DB、復元手順を記録する。接続文字列やパスワードは記録へ貼り付けない。
4. 可能であれば隔離環境へ復元し、テーブル件数と代表データを照合する。
5. 復元確認が終わるまで次へ進まない。

## 2. ショット数管理専用DBの用意

1. 旧DBとは別のPostgreSQLプロジェクト／データベースを新規作成する。
2. 用途が分かる名前を付け、旧アプリ用DBと取り違えないようにする。
3. 接続先の識別情報はパスワードを含まない方法で記録する。
4. 空DBであり、`molds`と`maintenance_logs`が存在しないことを確認する。

## 3. 空DBへのマイグレーション適用

トランザクション単位で、次の順に適用する。

1. `migrations/000_shot_schema.sql`
2. `migrations/001_p0_nullable.sql`
3. 本番用会社・管理者ユーザーを作成する
4. 既存ショットデータがある場合だけ、`company_id`と`created_by_user_id`を補完する
5. NULLが残っていないことを読み取り確認する
6. `migrations/002_p0_constraints.sql`
7. `migrations/003_counter_idempotency.sql`

適用後、`companies`、`users`、`memberships`、`auth_sessions`、`shot_molds`、`shot_records`と必要な制約・索引が存在することを確認する。失敗したトランザクションは原因を解消するまで再実行しない。

## 4. 本番用会社・管理者ユーザーの作成

1. 本番用の会社名、管理者ログインIDまたはメールアドレス、初期パスワードを承認者が決める。
2. 初期パスワードは十分な長さのランダム値にし、`0000`などのテスト用PINは使用しない。
3. 信頼できるローカル環境で`bcryptjs`を使い、パスワードのbcryptハッシュを生成する。平文パスワードをSQLファイル、Git、PR、Notion、ログへ保存しない。
4. トランザクション内で会社、ユーザー、`admin`ロールのmembershipを登録する。
5. ハッシュ値を表示する共有画面やログを残さず、登録後はログイン確認だけで検証する。

## 5. Render環境変数の設定

1. ショット数管理の本番サービスだけを対象にする。
2. `DATABASE_URL`へショット数管理専用DBの接続文字列を秘密値として設定する。
3. `PUBLIC_BASE_URL`へ確定したHTTPSの本番URLを設定する。末尾やパスを含めず、アプリの公開オリジンを使用する。
4. 旧メンテナンスサービスの`DATABASE_URL`は変更しない。
5. 設定画面では値を再表示・コピーせず、「設定あり」と対象サービス名だけを確認記録する。

## 6. デプロイ後の確認

1. デプロイ対象コミットSHAとGitHub Actions成功を照合する。
2. Renderのビルドと起動が成功し、ヘルスチェックが正常であることを確認する。
3. 本番管理者でログインできること、ログアウト後に保護画面へ戻れないことを確認する。
4. 未認証状態で保護URLを開き、ログイン画面へ誘導されることを確認する。

## 7. QR・スマホ実機確認

1. 検証用金型を1件登録する。
2. 生成QRが`PUBLIC_BASE_URL`配下の対象金型URLを指すことを確認する。
3. スマホ背面カメラでQRを読み取る。
4. 未ログインならログイン後に元の金型画面へ復帰することを確認する。

## 8. 累計値と差分履歴の確認

1. 検証用金型へ初回累計値を入力する。
2. さらに大きい累計値を入力し、履歴へ差分だけが保存されることを確認する。
3. 同じ値または小さい値が拒否されることを確認する。
4. 一覧、詳細、履歴の累計が一致することを確認する。

## 9. 会社間データ分離の確認

1. 検証専用の会社A・会社Bと、それぞれのユーザーを用意する。
2. 会社Aで作成した金型が会社Bの一覧へ出ないことを確認する。
3. 会社Bから会社Aの金型IDを直接指定し、詳細取得・更新・QR取得が拒否されることを確認する。
4. DB読み取りで各対象行に正しい`company_id`が付いていることを確認する。

## 10. 二重送信防止の確認

1. 同じリクエストIDで同一登録を再送する。
2. `shot_records`が1件だけ増え、累計が二重加算されないことを確認する。
3. 別リクエストIDの正しい次回入力は受け付けられることを確認する。

## 11. ロールバック

### アプリだけに問題がある場合

1. 新しいショット数管理サービスへの利用を停止する。
2. Renderで直前の正常コミットへ戻すか、新サービスを停止する。
3. 旧メンテナンスサービスは設定を変更していないため、そのまま継続する。
4. 専用DBは調査用に保持し、承認なしに削除・書き戻しをしない。

### 専用DBに問題がある場合

1. 新サービスを停止し、専用DBへの更新を止める。
2. 専用DBをバックアップしてから、直前スナップショットまたは検証済みdumpへ復元する。
3. 復元後に件数・累計・会社分離を再確認する。

### 旧アプリに影響が出た場合

1. 旧Renderサービスの設定変更を直ちに中止する。
2. 旧DBのバックアップと現在状態を比較する。
3. 承認者の判断後、検証済みバックアップから旧DBだけを復元する。
4. 原因が確定するまで新サービスの本番反映を再開しない。

## 現在の分離状況（2026-08-17 読み取り確認）

- 旧Renderサービス`mold-maintenance-app1`：`DATABASE_URL`設定あり。
- 本番候補Renderサービス`shot-count-manager`：`DATABASE_URL`設定あり、`PUBLIC_BASE_URL`設定なし、現在はビルド失敗状態。
- stagingサービス`shot-count-manager-staging`：`DATABASE_URL`と`PUBLIC_BASE_URL`設定あり。
- Neonには`mold-maintenance-app1`と`shot-count-manager-staging`の2プロジェクトが存在し、ショット数管理専用の本番プロジェクトは存在しない。
- 旧Neon DBには`molds`、`maintenance_logs`、`shot_molds`、`shot_records`が同居している。
- staging DBは別プロジェクトに分離されている。
- 本番候補サービスの秘密値は表示していない。現在の構成と既存記録から、新旧本番DBは分離済みとは判断できず、専用本番DBの作成と接続先切替が必須である。

旧DBでP0マイグレーションを実行すると、新テーブル側の変更であっても同じDBを共有する運用リスクが残る。旧アプリ・旧データへの直接変更を避けるため、本番反映は必ず専用DBで行う。
